# 2026-07-20 — Demo app: the same fake app, once per target

Shipped the demo-app half of backlog B2: [docs/specs/demo-app.md](../specs/demo-app.md) (seven required sections, implementation rules) and a self-contained `demo/` in **each example** — [examples/acme/demo/](../../examples/acme/demo/), [examples/cathode/demo/](../../examples/cathode/demo/) — static pages, no build step, framework runtimes from pinned CDNs, themed by that example's own compiled output. (First cut was a shared `examples/demo-app/` with a DS switcher; restructured per maintainer direction to per-example demos. Every file is byte-identical across the two `demo/` dirs except `assets/ds.config.js` and which target pages exist — that identity is now a spec rule.)

## What exists (per example)

- `index.html` — hub; all of the example's targets in side-by-side iframes, mode control, cross-link to the other example's hub for DS-vs-DS comparison.
- `bootstrap.html` (Acme only) / `daisyui.html` / `shadcn.html` — "Nimbus Console" (header, buttons, form, card, table, modal, ECharts chart) in each framework's idiom; per-page mode toggle wired to each target's own mode mechanism.
- `assets/ds.config.js` — the only DS-specific file: theme-asset paths, ECharts/daisyUI theme names, fonts, default mode (Cathode → dark), status notes.
- [examples/build-demo-themes.mjs](../../examples/build-demo-themes.mjs) — mechanical converter for artifacts that aren't browser-loadable: daisyUI `@plugin` blocks → `[data-theme]` rulesets; shadcn `@theme inline` font/radius lines → `:root`. Output committed under each `demo/themes/`; rerun after `transtyle build` (`npm run example:demo:themes`).

## Decisions & findings

1. **Two compiled artifacts aren't browser CSS.** The daisyUI exporter emits Tailwind-build input, and the shadcn exporter parks fonts/radius inside `@theme inline` (dropped by browsers as an unknown at-rule). Fine for their real consumers, but any "render the theme without a bundler" scenario (this demo, the future `transtyle preview`) needs the conversion step. Worth remembering when the preview site is designed — Phase 2 may want exporters to optionally emit a plain-CSS flavor.
2. **Bootstrap column doubles as an F13 exhibit.** The acceptance fixture's CSS-variable path rethemes the token tier only; `.btn-primary` stays stock blue on the page, correctly labeled. When the real Sass-path exporter ships, this page becomes its before/after.
3. **shadcn is rendered as its token contract** (hand CSS following the component recipes), not as Radix components — labeled on the page. Good enough for eyeballing color/radius/type; not a behavior test.
4. **Cathode ships no bootstrap page at all** — no compiled artifact exists (exporter unimplemented, no fixture), and per the B1 editorial policy a demo of nothing would mislead; the hub simply lists the targets that exist.
