# Implementation plan — 2026-H2 execution (from the strategic review)

**Audience: any implementer, including lower-capability AI models.** Rationale, evidence, and the assumptions each task tests (W1–W3) live in [docs/plan/strategic-review-2026-07.md](strategic-review-2026-07.md) — this document is the executable half: exact files, acceptance commands, dependencies. Where this document is silent, follow the referenced spec; if still ambiguous, stop and ask rather than invent.

**Non-negotiable process for every task (from CONTRIBUTING):**

1. One task = one commit series ending in a push to `main`; commit message starts `feat:`/`fix:`/`docs:` and names the task id (e.g. `feat: R3 …`).
2. Before committing: `npm run check:sync` passes; `npm run check:all` passes; determinism holds.
3. Worklog: add `docs/worklog/<date>-<task>.md` describing what was done and any deviation from this plan (deviations require a stated reason).
4. The meta-language principle applies throughout: nothing enters the shared catalog; new shared logic starts exporter-private.
5. Task states are tracked in the ROADMAP's **2026-H2 execution ledger**. Execute in dependency order; tasks with no mutual dependency may interleave.

> **Priority update (maintainer, 2026-07-22): R4 (npm publish) and R5 (public deploy) are parked until a good first alpha.** The near-term goal is a compiler that's genuinely good to use, not a published one. R1–R3 stand (R3 done, R2 drafted, R1 human-gated); R4/R5 wait, and every downstream task marked `Depends: R4` waits with them. Reassess when "first alpha" is defined.

### R2 — Freeze-readiness audit: IR spec v0 ready; plugin API deferred

**Draft landed 2026-07-22** ([ADR-0011](../adr/0011-v0-freeze-readiness.md), `proposed`); ratifies when R1 signs. **Depends:** R1 for ratification. **Files:** `docs/adr/0011-v0-freeze-readiness.md`; the drift banner on [plugins.md](../architecture/plugins.md); ADR index; this ledger.
The audit found the two surfaces are **not equally ready**, correcting this task's original "freeze both together" framing: every IR-spec guarantee is verified against a named CI script (freeze-ready, locks at R4); the plugin API spec materially diverges from the implemented `emit(normalizedIR, ctx) → { files, coverage }` interface, so its freeze is **deferred and gated on P1** (the conformance kit reconciles spec with reality). Per [ADR-0010](../adr/0010-pre-release-breaking-changes.md), the freeze *discipline* re-arms mechanically at first npm publication (R4), so what R4 locks is exactly the audited IR surface — no more.
**Acceptance (met for the draft):** ADR-0011 carries the verified-guarantee table with a CI-script citation per IR promise and an explicit exclusion + gate for every unready promise (plugin API → P1, schemas → R3, `transtyle.lock` → unimplemented); plugins.md carries the drift banner; `npm run check:all` passes. **Remaining for ratification:** R1 sign-off, then flip ADR-0011 to `accepted`.

### R3 — Real JSON schemas + strict options validation (audit A7 + A8)

**Depends:** R2 (schemas encode frozen shapes). **Files:** new `website/public/schemas/config/v0.json` and `report/v0.json` (generated by a new `scripts/gen-schemas.mjs`, checked in); `packages/core/src/load.js` (config validation); each exporter package declares an options schema consumed by the loader; tests under the existing test layout; [docs/specs/configuration.md](../specs/configuration.md) updated.
Constraint: core stays **zero-dependency** — no ajv. Hand-write a small internal validator that mirrors the published schemas; the schema files serve editors and the website, the validator serves the engine, and a test asserts the two agree on every fixture.
**Acceptance:** an unknown key in `targets.<name>.options` is an **error** (as configuration.md already promises), likewise unknown top-level config keys and unchecked `transtyle` manifest ranges (`irSpec`/`pluginApi`); all four examples' configs validate; `$schema` URLs in examples point at the real files; `npm run check:all` passes.

### R4 — npm publication of `@transtyle/*` (audit A5 + G3)

**Depends:** R2, R3. **Files:** all `packages/*/package.json` (publishConfig, provenance, files whitelist); a `scripts/release.mjs` or changesets setup; CHANGELOG.md; CONTRIBUTING release-process section.
Dry-run first, then publish all workspace packages with npm provenance attestations, in dependency order. Publishing is **human-gated**: a model prepares everything up to `npm publish --dry-run`; the maintainer runs the real publish.
**Acceptance:** `npm publish --dry-run` clean for every package; after the human publish, `npm i -g @transtyle/cli && transtyle --version` works from a clean machine; git tags pushed; release process documented.

### R5 — Website deployed on a real domain (audit F1)

## Phase B — Trust surfaces & the two experiments (months 2–4)

### P1 — Plugin conformance kit

**Depends:** R2 (the kit executes the frozen contract). **Files:** new `packages/plugin-kit/`; CI workflow extended; [docs/architecture/plugins.md](../architecture/plugins.md) gains a "conformance" section.
The kit is a runnable suite any exporter repo can point at its plugin: determinism (two runs byte-identical), coverage honesty (every emitted value traces to `native`/`derived`/`approximated`), mode handling (single- and multi-dimension fixtures), manifest range checking, unknown-option rejection (R3). Each rule cites the spec line it enforces.
**Reconciliation deliverable (from [ADR-0011](../adr/0011-v0-freeze-readiness.md) §2):** this task owns closing the gap ADR-0011 documented between plugins.md and the implemented interface. Either the spec drops to what's real (single `emit(normalizedIR, ctx) → { files, coverage }` hook, JS mappings, era-string manifest) or the implementation rises to the richer spec — decide per hook, and **remove the drift banner** from plugins.md once the spec and the kit agree. Only then is the plugin API a freezable surface (plugin API v1 is still declared at the Phase 2 exit, not here).
**Acceptance:** all 8 official exporters pass the kit in CI (`npm run check:all` includes it); the kit runs against an exporter *outside* the monorepo (prove with a scratch repo); every conformance rule carries a spec citation; plugins.md and the kit describe the same interface (banner gone).

### P2 — "Write your own exporter" tutorial

**Depends:** P1, R4. **Files:** new `website/src/docs/write-an-exporter.md`; nav; `scripts/check-sync.mjs` extended if the tutorial names exporters.
Zero → published third-party exporter, using `exporter-css-variables` as the reference and the P1 kit as the finish line. Written against **published npm packages only** — if the tutorial needs a monorepo path, that's a bug in R4.
**Acceptance:** executing the tutorial verbatim in a scratch repo outside the monorepo yields a kit-passing exporter without touching core; five-surface sync passes.

### P3 — Recruited third-party exporter pilot ← tests W1

**Depends:** P1, P2, R4, R5. **Files:** none in-repo initially; gap findings become issues; concluding `docs/findings/third-party-pilot.md`.
Human recruits a named partner (Mantine or Chakra per backlog B3). Every stumble is triaged as a release-blocking docs/API bug; API-change decisions from pilot feedback are the high-judgment calls (Fable).
**Acceptance:** one exporter shipped outside this repo using only public docs and packages (v1.0 exit criterion met), **or** a findings doc with the precise gap list and filed issues. Either outcome closes the task; only the first closes the criterion.

### P4 — Hostile-adoption experiment: a real DS with no published tokens ← tests W2

**Depends:** none technically; schedule after Phase A. **Files:** new `docs/findings/hostile-adoption.md`; a working extraction under a scratch dir, promoted to `examples/` **only** if it earns permanent-fixture status (which then triggers the five-surface demo obligations — don't promote casually).
Pick an OSS product with a hand-rolled design language (no token files, no semantic tier). Extract from its live CSS/Sass to `option.*` verbatim, bind the catalog, build all targets. Keep an honest **cost ledger** (hours-equivalent per step, where the [adopt-existing playbook](../../website/src/docs/adopt-existing.md) broke, what was judgment vs mechanical).
**Acceptance:** findings doc with cost ledger, playbook-breakage list, and an explicit verdict on W2 ("the wedge works as-is" / "importers must come first" / "playbook needs X"); Phase C order (I1 vs I2 first) decided and recorded in the ROADMAP ledger.

### P5 — Browser playground (audit E1 + E4)

**Depends:** R4, R5. **Files:** new `website/src/playground/` (Astro island); a browser entry export in `packages/core`; nav.
Core is zero-dep ESM — it runs client-side unchanged. Paste tokens → live css-variables + shadcn output, coverage bar, `explain`-on-hover; doubles as the report.json viewer.
**Acceptance:** playground works on the deployed site with no server round-trip, importing the *published* npm ESM; Acme's tokens pasted in reproduce `examples/acme/dist/` output byte-identically.

### P6 — `transtyle diff` (semantic DS diff, per-target impact)

**Depends:** R2 (diff semantics build on frozen IR). Two commits: spec, then implementation. **Files:** new `docs/specs/diff.md`; `packages/cli` + `packages/core` diff module; golden tests alongside `check-cli`; website CLI page.
Spec first (Opus): what constitutes a breaking design change; how impact propagates through derivation provenance to per-target output. Implementation (Sonnet) follows the spec, not vice versa.
**Acceptance:** `transtyle diff <ref>` between two versions of an example produces the spec's documented impact summary; golden test in `check:all`; sync rule applied (CLI page).
