# Proposal 0005 — A border ladder, an inverse pair, and why icons stay on the text ladder

**Status: accepted, implemented 2026-10-09** ([#31](https://github.com/transtyle/transtyle/issues/31), [#33](https://github.com/transtyle/transtyle/issues/33), [#36](https://github.com/transtyle/transtyle/issues/36)). Six semantic slots promoted: `semantic.color.border.{subtle, base, strong, field}` and `semantic.color.inverse.{surface, text}`. The single `semantic.color.border` leaf is renamed in place to `border.base` ([ADR-0010](../adr/0010-pre-release-breaking-changes.md)). A third candidate, an `icon.*` colour ladder, is rejected: the systems that name icon colours give them their text colours, so the icon colours two exporters had stuck at their own defaults are bound to the existing text ladder instead.

The three were studied together because they are the same kind of question about the same part of the catalog, the neutral content colours around `text.*`, and the answers have to agree: a ladder for borders next to the one for text, a pair for inverted content, and no separate ladder for icons.

## The bar

[CONTRIBUTING](../../CONTRIBUTING.md#principles-that-constrain-changes): new catalog vocabulary is validated against several independent ecosystems, never derived from one library's naming, and exporters translate by meaning. [Proposal 0001](0001-universal-token-ir.md)'s convergence study is the model: a meaning several unrelated systems arrived at, with the same shape, is a fact about design systems; a name one library uses is not.

Evidence below was read in each system's source on its default branch, pinned to a commit. The border and icon tables were first checked on 2026-10-06 (on the issues' refinements) and re-checked on 2026-10-09; the inverse table was read on 2026-10-09.

Eleven systems, none borrowing from another, separate borders by **strength** (a lighter one for separators, a default, sometimes one at 3:1) and most name the **field border at rest** apart from the rest. That is the shape promoted.

Two citations in the issue were wrong and are not evidence: Carbon's `border-interactive` is the blue border of a _focused_ input (Blue 60, Blue 50 on G100), not a field at rest; Ant's `controlOutline` is the focus box-shadow colour, which belongs with `ring`.

### Slots and rules

| Slot            | Default when unauthored                                                                                                               | Rule name                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| `border.base`   | `text.base` mixed 0.88 toward `elevation.1.surface`                                                                                   | `mix-toward-surface(0.88)` |
| `border.subtle` | `border.base` mixed 0.50 toward `elevation.1.surface`                                                                                 | `mix-toward-surface(0.50)` |
| `border.strong` | the smallest 0.01 step from `border.base` toward `text.base` that reaches 3:1 against `elevation.0.surface` and `elevation.1.surface` | `contrast-walk(3:1)`       |
| `border.field`  | `border.base`                                                                                                                         | `alias(border.base)`       |

- **`base` from the text, like daisyUI.** The four examples' hand-authored borders measure as `text.base` mixed 0.79 to 0.92 toward the surface (Acme 0.92 / 0.90, Cathode 0.86 / 0.79, GOV.UK 0.85, Carbon 0.92 / 0.89); 0.88 is the middle. Before this proposal the slot had no rule at all, so a minimal design system had no border and every exporter dropped its border variables.
- **`subtle` and `strong` from `base`,** not from `text.base`: a fixed ratio from the text can land above an authored `base`, and the ladder would turn upside down.
- **`strong` is a contrast target**, the kind of walk `on-tint` already does, because what makes a strong border is WCAG 2.2 SC 1.4.11 (3:1 for the boundary of a component), not a ratio. On the examples it lands between 3.02:1 and 3.63:1. It finds Carbon's own value without being told: #8b8b8b on White (Carbon's `border-strong-01` is #8d8d8d) and #707070 on G100 (Carbon: #6f6f6f). No measured authored border in the examples reaches 3:1; this is the first cell that does.
- **`field` is an alias**, so every example keeps its output. A design system that wants accessible fields aliases it to `{semantic.color.border.strong}`.

**Ladder against role outlines.** The role grid's `<role>.outline` / `outline-hover` cells stay the role-tinted borders (outlined buttons, alerts, Radix's per-hue steps 7 and 8). The ladder is the content borders. Same split as `text.*` against `<role>.text`.

### Names (Julien, 2026-10-07)

- **`field`, not `interactive`**: `interactive` is a false friend of Carbon's blue focus border. `field` is the catalog's own family word (`radius.field`), and PrimeNG's (`formField`) and daisyUI's (`--radius-field`).
- **Rename in place**: `semantic.color.border` becomes `semantic.color.border.base`, with no alias. DTCG 2025.10 §6.1 forbids a token that is also a group, so keeping the old leaf next to the new children would need alias machinery in NORMALIZE, which ADR-0010 rules out before the first stable release. A token left at the old path is an error, `TST1125`, naming the new one.
- **The loader now reports the half-done migration.** Writing `border: { "$value": …, "subtle": {…} }` used to compile without a word and drop the children: the loader stops at `$value`. It is now `TST1312`, an error, for any token, as the DTCG specification requires.

### Bindings

| Target           | Binding                                                                                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| shadcn/ui        | `--border`, `--sidebar-border` ← `base`; `--input` ← `field` (was `approximated` against the single border; now `derived` while it aliases `base`, `native` once authored)                                                      |
| Bootstrap        | `$border-color` ← `base`. `$input-border-color` stays on `var(--bs-border-color)`: it has no `--bs-*` counterpart, so binding `field` would bake the light value into dark mode. `$border-color-translucent` is an alpha border |
| PrimeNG          | `formField.borderColor` ← `field`; `content` and overlay `borderColor` ← `base`. They read `neutral.outline` before, so an authored border never reached PrimeNG; the field hover stays on `neutral.outline-hover`              |
| Storybook        | `appBorderColor`, `buttonBorder` ← `base`; `inputBorder` ← `field`                                                                                                                                                              |
| Chakra UI        | `border` ← `base`; `border.subtle` ← `subtle` (was the neutral tint, `approximated`). `border.emphasized` stays on `neutral.outline`: Chakra's is gray 300, one step above its default, far from a 3:1 boundary                 |
| Mantine          | `--mantine-color-default-border` and the gray tuple's step 4 ← `base`; Mantine's inputs read that step, so there is no separate field border to set                                                                             |
| Material UI      | `divider`, `TableCell.border` ← `base`; the outlined input's border is a fixed alpha in its component styles, not a palette key                                                                                                 |
| ECharts, daisyUI | axis and split lines ← `base`; daisyUI's `--color-base-300` stays `approximated` from `base` (a third background step, not a border)                                                                                            |
| Radix            | none: steps 6 to 8 are per hue and come from the role grid                                                                                                                                                                      |
| CSS variables    | every slot: `--color-border` becomes `--color-border-base`, plus three new variables per mode                                                                                                                                   |

**Left out, on purpose.** A field _hover_ border (PrimeNG `hoverBorderColor`, Fluent `Stroke1Hover`, Radix step 8): an example that aliases `field` to `strong` gets a PrimeNG hover lighter than its rest state, because the hover reads `neutral.outline-hover`. Disabled and inverse borders (Carbon `border-disabled`, `border-inverse`): see [#35](https://github.com/transtyle/transtyle/issues/35) for disabled, and part 2 for inverse.

Five systems, the two component-heavy targets this repository exports to among them, paint the same thing: the darkest neutral on a light page, the lightest on a dark one, with the page colour on top. Material, Carbon and Fluent name it; Bootstrap and PrimeNG hard-wire it. Three rows of the issue's list did not hold: Spectrum has no inverse background token (only two icon foregrounds, `icon-color-inverse` deprecated), GOV.UK has an `inverse-text` colour but no inverse surface (white text on brand or success), and Fluent's _tooltip_ uses theme-invariant "static" tokens rather than the inverted pair (its inverted Toast does use it). Aura's tooltip is not an inverse either: `surface.700` on `surface.0` in both schemes.

### Slots and rules

| Slot              | Default when unauthored | Rule name                    |
| ----------------- | ----------------------- | ---------------------------- |
| `inverse.surface` | `neutral.text-strong`   | `alias(neutral.text-strong)` |
| `inverse.text`    | `elevation.0.surface`   | `alias(elevation.0.surface)` |

Defaulting by alias, not by reading the other mode, is what the two targets already do: Bootstrap's tooltip is `--bs-emphasis-color` on `--bs-body-bg`, which this compiler drives from those two slots, and PrimeNG's `contrast` severity read the same pair through a private convention. So every unauthored output stays the same, a single-mode system (GOV.UK) gets a coherent pair with no lightness flip, and what the slots add is the authored case. `inverse.text` on `inverse.surface` joins the contrast-checked pairs (`TST2101`): 13.6:1 to 19.6:1 on the examples' defaults, 11.5:1 and 16.4:1 on Carbon's authored pair.

### Scope (Julien, 2026-10-07)

- **Two slots now.** `inverse.primary` (Material's `inverse-primary`, Carbon's `link-inverse`) and `inverse.border` (Carbon's `border-inverse`) have no consumer on either reference target; they wait for one.
- **`text.inverse` stays its own slot.** It is the other mode's `text.base`, what Storybook's `textInverseColor` wants; what the targets put on an inverse surface is the page colour. Folding one into the other would move either the Storybook fixture or every tooltip.

### Bindings

| Target        | Binding                                                                                                                                                                                                                                                                                                                                               |

Authored, both paths write the light value and a `[data-bs-theme="dark"] .tooltip` block: a Sass variable can't flip with the mode, and the component walk would bake the light bubble into dark mode |
| PrimeNG       | the `contrast` severity reads `inverse.*` (same output by default). The tooltip is bound per mode only when the pair is authored: Aura's tooltip is a dark bubble in both schemes, and binding the defaults would darken every tooltip                                                                                                                |
| Chakra UI     | `bg.inverted` ← `inverse.surface` (was `text.strong`, `approximated`); `fg.inverted` ← `inverse.text` (was `text.inverse`: Chakra's tooltip is `fg.inverted` on `bg.inverted`)                                                                                                                                                                        |
| Mantine, MUI  | a `dropped` row: Mantine's tooltip reads fixed tuple steps in its stylesheet, MUI's a fixed grey 700 in both schemes; neither is a theme variable                                                                                                                                                                                                     |

The Carbon example authors the pair from Carbon's own `$background-inverse` / `$text-inverse`, so its Bootstrap, PrimeNG and Chakra demos show Carbon's real tooltips in both schemes.

## 3. Icon colours: not a catalog ladder

[#36](https://github.com/transtyle/transtyle/issues/36) proposed `icon.{base, muted, disabled, inverse, on-color}`. The systems that name icon colours give every one of these rungs its text value:

| System                                                                                                                                                     | Icon token                                                         | Equals                                                                                                             |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| [Carbon 11](https://github.com/carbon-design-system/carbon/blob/52ed33564c90e00d2cda219cf38ba52abc9b690d/packages/themes/src/dtcg/themes.json#L1313-L1415) | `icon-primary`, `-secondary`, `-disabled`, `-inverse`, `-on-color` | `text-primary`, `-secondary`, `-disabled`, `-inverse`, `-on-color`, in White and G100, the disabled alpha included |
| [Spectrum](https://github.com/adobe/spectrum-design-data/blob/eba428d462bfb5a3288835cb6cf0dcb1c4dc93af/packages/tokens/src/icons.json#L891-L896)           | `icon-color-primary-default`                                       | an alias of `neutral-content-color-default`                                                                        |
| Fluent 2, Material 3                                                                                                                                       | none for these rungs                                               | icons read the foreground / `on-surface-variant` colours                                                           |

The names exist; distinct values don't. The icon colours that differ from text are role colours (Carbon's `icon-interactive`, Spectrum's per-hue icons), which the role grid already covers. A group whose every default equals the text ladder and that no measured system gives another value would be permanent vocabulary with nothing to say. **Decision (Julien, 2026-10-07): bind the icon colours to the text ladder, no new vocabulary.** Icon colour joins icon size (proposal 0004) as a watch item: it is promoted when a source system gives its icons values of their own.

What changed in the exporters instead, both of them slots that kept the target's own default while the report said otherwise:

- **Bootstrap.** `$btn-close-color` and `$form-select-indicator-color` read `text.base` (both are base-rung glyphs; Bootstrap dims the close glyph with its own opacity, so the muted rung would dim it twice). They were reported "derived via driven roots" but stayed at `$black` and `$gray-800`, which nothing drives. Both are baked into SVG data URIs, so Sass path only; the dark chevron already follows the driven `$body-color-dark`, and the dark close glyph is Bootstrap's filter over the light one (`approximated`).
- **PrimeNG.** `formField.iconColor`, `list.option.icon.{color, focusColor}`, `navigation.item.icon.activeColor` and `navigation.submenuIcon.*` read `text.muted` at rest and `text.base` on focus or when active, as Aura's own `surface.400` / `surface.500` pair does. 34 component slots that referenced them (icon fields, input-group addons, clear icons, dropdown chevrons, menu icons) now follow the design system instead of Aura.
